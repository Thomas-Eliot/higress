# 插件配置分片设计 - 通用方案（原始设计）

> 本文档记录原始设计方案。该方案基于模板变量替换，具有更好的通用性，可适用于任意插件类型的分片场景。当前实现采用了不同的路径（见差异部分），但本方案作为未来演进方向保留。

## 背景

目前网关用 istio 的 WasmPlugin 来实现一些能力，但这个 WasmPlugin 资源太大超过了 etcd 的存储限制（1.5MB），需要修改 istio 里的实现，设计一个机制，让这个配置可以切片分到多个 ConfigMap 里。目前遇到这个问题的场景主要是：

- 实现消费者的认证鉴权能力，目前消费者数量压测到 8K
- 实现 REST to MCP Server 的配置能力，目前 MCP Server 数量压测到 400

## 核心设计：基于模板变量替换

deepwiki 参考：[https://deepwiki.com/search/-yaml-apiversion-extensionsist_014f396b-ef23-48a7-a346-22baafd3d38d](https://deepwiki.com/search/-yaml-apiversion-extensionsist_014f396b-ef23-48a7-a346-22baafd3d38d)

### 配置方式

基于模版变量替换的方式，Controller 读取 ConfigMap 数据后渲染模板中的占位符，生成最终的 `pluginConfig`：

```yaml
apiVersion: extensions.istio.io/v1alpha1
kind: WasmPlugin
metadata:
  labels:
    istio/cluster-id: gw-xxxxxx-istio
  name: apig-inner-key-auth-xxxxxx
  namespace: xxxxxx
spec:
  imagePullPolicy: Always
  phase: AUTHN
  # 新增字段，用于渲染模版里的参数
  resourceRefs:
  - consumer-configmap1
  - consumer-configmap2
  resourceTemplateSchema:
  - key: consumer
    value: consumer-placeholder
  - key: rbacrule
    value: rbac-placeholder
  # 新增字段，渲染后才生成pluginConfig，pluginConfig改成非必填
  pluginConfig:
    consumers:
    {.consumer-placeholder}
    global_auth: false
    keys:
    - placeholder
    rbac_rules:
    {.rbac-placeholder}
```

`pluginConfigTemplate` 和 `pluginConfig` 是 oneOf 关系，如果定义了模板，则基于 `resourceRefs` 中的 ConfigMap 数据来渲染后生成最终的 `pluginConfig`：

```yaml
apiVersion: extensions.istio.io/v1alpha1
kind: WasmPlugin
metadata:
  labels:
    istio/cluster-id: gw-xxxxxx-istio
  name: apig-inner-key-auth-xxxxxx
  namespace: xxxxxx
spec:
  imagePullPolicy: Always
  phase: AUTHN
  pluginConfig:
    consumers:
    - credentials:
      - Bearer apemvnbARpfjE6LN
      in_header: true
      in_query: false
      keys:
      - Authorization
      name: tetetetete
    - credentials:
      - apikey-zl06-yace-0
      in_header: true
      in_query: false
      keys:
      - apikey-zl06-yace-0
    global_auth: false
    keys:
    - placeholder
    rbac_rules:
    - permissions:
      - or_rules:
        - route_name:
            exact_match: test@echo
      principals:
      - or_rules:
        - consumer: tetetetete
    - permissions:
      - or_rules:
        - route_name:
            exact_match: autoDefault@route-consumer006
      principals:
      - or_rules:
        - consumer: apikey-zl06-yace-1847
```

### 分片数量控制

按 10W 消费者和 1W MCP Server 的要求，且分片后单个 ConfigMap 的资源大小限制在 200KB 内（[@尙书](https://www.yuque.com/shangshu.xiaoss)建议值），至少需要 186 个分片。建议分片总数可以限制为 200。实现相关注意事项：

- Istio 在监听 ConfigMap 时需要按 label 过滤，只监听本网关集群关联的 ConfigMap，避免配置生效速度过慢（这里需要做一下测试，对比下分片前后生效速度的影响，以及集群里 ConfigMap 数量达到最大时，生效速度最慢是多少，有个底）
- 关联 ConfigMap 内容变更会触发插件配置更新，所以如果控制台的分片逻辑未来发生调整重构（例如使用 Hash 分片策略后，100 个分片总数不够，需要 reHash），则不能对已经创建的 ConfigMap 做修改，要重建完所有新的 ConfigMap，更新完插件配置，最后再删除之前分片逻辑创建的 ConfigMap
- 这里的模版变量替换和配置中的 [KMS Secret 变量替换](https://aliyuque.antfin.com/gvr7dx/cr0xgb/vmfctxpgdwcfie5l#sIWAI) 不冲突，实现机制上需要先进行模版变量替换生成控制面的 pluginConfig，然后在下发给 Envoy 的 xDS 配置时进行 KMS secret 等变量替换

### 分片策略

分片策略主要由控制台设计实现，目前看有两种常见分片方式，各有优劣：

#### 按资源在数据库的递增 ID 分片

优势：ConfigMap 的分片数跟随资源数线性增长，在资源数不多的情况下，ConfigMap 数量可以得到有效控制

劣势：如果用户对资源做批量删除和重建，会导致 ConfigMap 数量不可控，这里可能需要做比较复杂的设计

#### 按资源在数据库的 Key 做 Hash 分片

优势：ConfigMap 总量可控，而且可以做 reHash，实现简单可依赖

劣势：极端情况下，100 个资源就会有 100 个分片，集群里的 ConfigMap 数量会快速增加

## 与当前实现的差异

当前实现（详见 [插件配置分片设计-实现总结.md](./插件配置分片设计-实现总结.md)）在落地时做了以下调整：

| 设计项 | 本方案（通用设计） | 当前实现 |
|--------|-------------------|----------|
| 模板渲染方式 | `pluginConfig` 中使用 `{.placeholder}` 占位符，Controller 渲染模板 | 不使用模板占位符，Controller 直接合并 ConfigMap 数据到 `defaultConfig` 和 `matchRules` |
| 分片数量 | 建议 200 个 | 固定 64 个（`SHARD_COUNT = 64`） |
| 分片策略 | 讨论了按 ID 和按 Hash 两种 | 按 consumer name 的 MurmurHash % 64 |
| ConfigMap 命名 | `consumer-configmap1` 等 | `hi-key-auth-shard-{0..63}` |
| 路由开关 | 未单独设计 | 独立 ConfigMap `hi-key-auth-route-switches` 管理 configDisable |
| CR 中的 pluginConfig | 保留模板格式 | 分片模式下 CR 不保留 matchRules 和 consumers，全部由 ConfigMap 提供 |
| rbac_rules | 建议按 consumer 维度重组 | 实现为 matchRules 中的 `allow` 列表（按 route 聚合 consumer names） |
| 适用范围 | 通用，可适用于任意插件类型 | 特化于 key-auth 场景 |

### 本方案的优势

1. **通用性**：模板渲染机制不绑定具体插件逻辑，任何需要分片的插件都可以复用同一套 Controller 代码
2. **解耦**：Controller 不需要理解具体插件的配置语义，只做模板替换
3. **扩展性**：新增插件分片只需定义模板和 ConfigMap 结构，无需修改 Controller 合并逻辑
4. **MCP Server 分片**：本方案天然支持 MCP Server 配置的分片（`_rules_` 数组的模板替换）

### 当前实现的优势

1. **实现简单**：直接合并，不需要模板解析引擎
2. **语义明确**：Controller 理解 consumers/matchRules 的结构，可以做更精细的合并（如按 route 聚合 allow 列表）
3. **路由开关独立管理**：configDisable 与授权数据分离，增量操作更高效
